主持人：你把它做在终端里，只是因为这是最快能把东西跑起来的方式。

Boris：对，因为我不用写 UI。

主持人：明白。

主持人：这挺迷人的。我的意思是，Claude Code 能在这么优雅、简单的形态下工作得这么好，其实挺反直觉的。终端已经存在很久了，而它似乎成了一个很好的设计约束，反而催生了很多有趣的开发者体验——它不像是在干活，作为开发者你就是觉得好玩。我不用去想文件在哪、一切在哪，而这几乎是个意外。

Boris：对，那是个意外。我记得，在终端形态开始在内部流行起来之后——说实话，做出这东西大概两天，第一个原型出来两天后，我就开始把它给团队用，做 dogfooding，因为你知道，你想出一个点子、它看起来有用，你第一件想做的就是把它给别人，看他们怎么用。然后第二天我一来，坐我对面的 Robert，他也是工程师，他电脑上已经装着 Claude Code 了，而且正在用它写代码。我当时：「你、你在干嘛？这东西还没准备好，只是个原型。」但它在那个形态下就已经有用了。我还记得我们做发布评审、准备对外发布 Claude Code 的时候，那是 2024 年 12 月、11 月左右，Dario 问：「内部的使用曲线，那个 DAU 曲线，几乎是垂直的。你是不是在强迫工程师用它？你是不是在强制要求？」

Boris：我就说：「没有没有，我们没强制。我就是发了个帖子，然后他们就互相传开了。」说实话，真的就是个意外。我们从 CLI 起步，因为它是最便宜的做法，然后它就在那待了一阵子。

主持人：那在 2024 年那段时间，工程师们是怎么用它的？他们已经在用它发布代码了吗，还是用别的方式？

Boris：那时候模型写代码还不行。我个人主要拿它来自动化 git。到这个时候，我大概已经把 git 忘得差不多了，[笑声] 因为 Claude Code 已经替我干了太久。不过确实，自动化 bash 命令是非常早期的用法，还有操作 Kubernetes 之类的东西。也有人拿它写代码，已经有一些早期迹象。我想第一个用例其实是写单元测试，因为风险相对低一些，而模型写得仍然挺烂的。[笑声]

Boris：但大家还是在摸索，慢慢搞明白怎么用这个东西。

Boris：我们还看到一件事：大家开始给自己写 markdown 文件，然后让模型去读那个 markdown 文件。这就是 CLAUDE.md 的由来。对我来说，做产品最大的一个原则可能就是「潜在需求（latent demand）」。这个产品的几乎每一点，都是在最初的 CLI 之后，通过潜在需求长出来的。CLAUDE.md 就是一个例子。还有另一个普遍原则，我觉得可能挺有意思：你可以为模型本身而构建，也可以在模型外面搭一层脚手架（scaffolding），把性能往上提一点——取决于领域，可能提升 10%、20% 之类——然后基本上，下一代模型一出来，这点增益就被抹平了。所以你要么搭脚手架、拿到一点性能提升、然后再重建一遍；要么就等下一代模型，相当于白拿。CLAUDE.md 和这类脚手架就是例子。说真的，我觉得这也是为什么我们一直待在 CLI 里——因为我们觉得，没有任何我们做得出来的 UI，在六个月后还会有意义，因为模型进步太快了。

主持人：刚才我们还说要互相比较一下 CLAUDE.md，但你说了句挺深刻的话：你的其实非常短，几乎和大家以为的相反。为什么？你的 CLAUDE.md 里写了什么？

Boris：好，我来之前特意查了一下。我的 CLAUDE.md 有两份——其中一份就两行。第一行是：每次你提 PR，就开启 automerge，这样只要有人一通过，它就合并了。这样我就能一直写，不用来回折腾 code review 之类。第二行是：每次我提 PR，就把它发到我们内部团队的 stamp 频道，这样有人能给我盖个章、我就能解除阻塞。核心想法是：除此之外的所有指令，都在我们提交进代码库的那份 CLAUDE.md 里，整个团队每周都会往里贡献好几次。我经常看到某个人的 PR 里犯了个完全可以避免的错误，我就会直接在 PR 上 @Claude，写一句「加到 CLAUDE.md 里」，我一周会干很多次。

主持人：你会压缩 CLAUDE.md 吗？我肯定遇到过顶上弹出提示说「你的 CLAUDE.md 已经几千个 token 了」。你们碰到这种情况怎么办？

Boris：那你觉得呢？现在是不是太啰嗦了？

主持人：哦，我很喜欢这种啰嗦，因为有时候它就是会一路跑偏，我在旁边看着，我能很快地读，然后发现「哦，不对不对，不是这个」，我就按 Escape 把它停下来，然后它就停下，整整一窝 bug 就在发生的过程中被拦住了。我是说，通常那都是我没把 plan mode 用好的时候。

Boris：这个我们大概经常改。我记得很早的时候，大概六个月前，我试着在内部把 bash 的输出直接去掉、只做总结，因为我觉得，那些又臭又长的 bash 命令我根本不关心。结果我把它给 Anthropic 的员工用了一天，大家都造反了。[笑声] 我想看我的 bash，因为它其实挺有用的——比如 git 的输出可能没啥用，但如果你在跑 Kubernetes 任务之类的，你确实会想看到。我们最近把文件读取和文件搜索隐藏了，所以你会注意到，它不再说「read foo.md」，而是说「读取了 1 个文件」「搜索了 1 个模式」。而这件事，我觉得六个月前我们是没法发布的，因为那时候模型还没准备好，它还是会经常读错东西，作为用户你还得盯着、抓它、调试它。但现在我发现，它几乎每次都走在正确的方向上。正因为它工具用得这么多，做个总结反而好得多。但我们就这么发出去了，自己 dogfood 了大概一个月，然后 GitHub 上的人不喜欢。有个很火的 issue，大家说「不行，我想看细节」，那真是特别棒的反馈。于是我们加了一个新的 verbose mode，就在 /config 里，你可以开启 verbose mode，如果你想看所有文件输出，你仍然可以那样做。然后我又在那个 issue 里回了帖，结果大家还是不喜欢——这又是一件特别棒的事，因为世界上我最喜欢的事，就是听大家的反馈，听他们到底想怎么用它。于是我们就一遍、一遍、又一遍地迭代，把它做到真正好、做到大家想要的样子。我现在都很惊讶，我居然这么享受修 bug。而你要做的，只是有非常好的日志，然后哪怕就说一句「嘿，去看看那个对象，它在这一点上搞错了」，它就会去搜日志，把一切都搞清楚。它能进到你的——你可以建一个 production 隧道，它会帮你去看 production DB。这太疯狂了。修 bug 正在变成：去 Sentry 复制 markdown。很快，它就会直接是 MCP。就像是自动修 bug、自动生成测试的那种——那个新词叫什么来着——「开创业工厂」。哦对。

主持人：对。现在有这么多理念：与其去 review 代码，不如——我这个人比较老派，所以我喜欢那种啰嗦。我喜欢说：「哦，你在做这个，但我想要你做那个。」对吧？但现在有一种完全不同的思路：任何时候，只要一个真人还得去看代码，那就是坏事。

主持人：这挺迷人的。

主持人：那你会给技术型创始人什么建议，让他们真正成为最新一代模型的「极致主义者」？听起来，那些刚从学校出来、或者没有任何成见的人，可能比那些干这行很久的工程师更适合。那专家要怎么变得更好？Boris：我觉得对你自己来说，这是一种「初学者心态」，还有——我不知道——也许就是谦卑。我觉得工程师这门行当，我们已经学会了持有非常强烈的观点，而资深工程师还会因此得到奖励。我以前在大公司工作的时候，招架构师、招这类工程师，你要找的就是那种经验丰富、观点极强的人。但事实证明，这些东西很多都已经不再相关了，很多观点都应该改变，因为模型在变得更好。所以我觉得，最重要的能力，其实是那些能用科学的方式思考、能从第一性原理出发思考的人。

主持人：那你现在给团队招人的时候，怎么筛选出这种人？

Boris：我有时候会问，能不能举一个你犯错的例子。这是个特别好的问题。一些经典的行为面试问题——甚至都不是编程题——我觉得相当有用，因为你能看出一个人事后能不能意识到自己的错误，能不能认领这个错误，以及有没有从中学到东西。而很多非常资深的人，尤其——也有一些创始人类型是这样，但我觉得创始人其实总体上还挺擅长这个的。但有些人，他们永远不会真正为错误承担责任。不过对我自己来说，我不知道，我大概有一半时间是错的。我一半的点子都是烂点子，你就是得去试，试一个东西、交给用户、和用户聊、学习，然后最终你可能会落到一个好点子上，有时候也不会。而这种能力，我觉得过去对创始人来说非常重要，但现在我认为，它对每一个工程师都非常重要。

主持人：你觉得，你会不会有一天，根据一个人和智能体协作的 Claude Code  transcript 来决定要不要招他？因为我们现在就在这么做。我们刚加了一个测试性的环节：你可以上传一段你用 Claude Code、Codex 或别的什么写某个功能的 transcript。我个人觉得这能行得通。我的意思是，你能看出一个人是怎么思考的——他到底看不看日志；智能体跑偏的时候，他能不能把它拽回来；他用不用 plan mode；他用 plan mode 的时候，有没有确保有测试——所有这些不同的东西……

Boris：那真是个很高的赞美。对对，它就应该让你感觉像是在发现新东西。

主持人：发现《Lord of the Red Dragon》。太棒了。我的天。

Boris：对。但我们就是得自己摸索出这一整套给终端做东西的 UX 原则，因为几乎没人写这些东西。如果你去看 80 年代、90 年代、2000 年代那些大型终端应用，它们用的是 curses，有一堆窗口之类的东西。按今天的标准看，就是有点 janky，显得太重、太复杂。所以我们不得不把很多东西重新发明一遍。比如终端的 spinner——就那个 spinner 的小词——到现在大概已经迭代了，我想说，50 次、也许 100 次。其中大概 80% 都没发布。我们试一下，感觉不对，换下一个；再试，感觉不对，再换。而这也正是 Claude Code 最惊人的地方之一，对吧？你可以写这些原型，可以一口气做 20 个原型，看你喜欢哪个，然后发那个，整个过程可能就几个小时。

主持人：而换在过去，你得用 Origami 或者 Framer 之类的工具，大概做三个原型，花上两周。就是慢得多得多。

Boris：所以我们拥有这种奢侈：我们得去发现一个新东西，得做一个东西，我们还不知道正确的终点在哪，但我们能极快地迭代到那里，而这让它变得非常容易，也让我们能做出一个让人愉悦、大家爱用的产品。

主持人：Boris，你本来还有别的建议要给 builder，但我们一直打断你，因为我们问题太多了。[笑声]

Boris：我想说——好吧，也许就两条建议，有点怪，因为它们都关乎「为模型而构建」。第一条是：不要为今天的模型而构建，要为六个月之后的模型而构建。这有点怪，对吧？因为如果产品现在跑不通，你是不可能找到 PMF 的。但这恰恰是你该做的事，因为否则的话，你花一大堆功夫，为「现在」这个产品找到了 PMF，然后你就会被别人 leapfrog（超越），因为他们在为下一代模型而构建，而新模型每隔几个月就会出来。去用那个模型，去摸清它能做什么的边界，然后为你认为六个月之后会成为现实的那个模型而构建。我想第二条是——其实就在 Claude Code 团队，我们坐的那片区域，墙上挂着一幅裱起来的《The Bitter Lesson》。是 Rich Sutton 那篇，我觉得每个人都该读一读，如果你还没读。它的核心意思是：更通用的模型永远会胜过更专门的模型。它有很多推论，但归结起来就是一句话：永远不要和模型对赌。所以我们一直在想一件事：我们可以在 Claude Code 里做一个功能，可以让它作为产品变得更好——我们管这叫 scaffolding（脚手架），也就是所有那些「不是模型本身」的代码。但我们也可以就等几个月，模型自己大概就能做那件事了。这永远是个取舍，对吧？是现在投入工程工作，把能力往外推一点点——在你想扩展的那张蜘蛛图上，某个领域里也许推个 10%、20%；还是你就等，下一代模型就会做到。所以要一直用这种取舍去思考：你到底想投在哪里，并且要假设，不管那脚手架是什么，它终究只是技术债（tech debt）。

主持人：你们大概多久重写一次 Claude Code 的代码？是每六个月就来一次吗？[笑声]

主持人：有没有那种你已经删掉的脚手架，因为你不再需要它了，因为模型就是变好了？

Boris：太多了。对，Claude Code 的全部代码就是写了又重写、重写了又重写，一遍又一遍。我们每隔几周就下线（unship）一些工具，每隔几周又加一些新工具。Claude Code 里没有任何一部分是六个月之前就存在的。它就是一直在被重写。

主持人：那你会不会说，现在 Claude Code 的代码库里，大部分——比如 80%——都只有几个月的「年龄」？

Boris：对，绝对是。甚至可能还不到——嗯，也许就几个月。感觉差不多是这个数。

主持人：所以这就是现在代码的生命周期。这又是一条 alpha：要预期它的「保质期」就只有几个月。

Boris：对。

主持人：对最优秀的创始人来说是这样。

主持人：你看到 Steve Yegge 那篇讲在 Anthropic 工作有多爽的帖子了吗？里面有一句说，一个 Anthropic 工程师现在的产出，平均是 Google 巅峰时期一个 Google 工程师的 1000 倍——这数字真的离谱，1000 倍啊。我们三年前还在聊 10 倍工程师，现在聊的是在一个正值巅峰的 Google 工程师之上再乘 1000 倍 [笑声]，这真的难以置信。Boris：是啊，内部你看那些技术岗的员工，他们每天都用 Claude Code。就连非技术岗的员工，我想销售团队大概有一半也在用 Claude Code。他们已经开始转向 co-work，因为它更好用一些，有个 VM，所以更安全一点。不过确实，我们刚拉了一个数据：团队去年规模翻了一倍，但「人均工程师产出」涨了大概 70%。

主持人：是用什么衡量的？

Boris：就是最简单、最笨的指标：pull request。不过我们也会用 commit、commit 的生命周期之类的东西交叉验证一下。而自 Claude Code 出来以后，Anthropic 的人均工程师产出涨了 150%。

主持人：我的天。

Boris：而这太疯狂了，因为我上份工作，在 Meta，是负责代码质量的。

Boris：当时我负责的是我们所有产品、所有代码库的质量——Facebook、Instagram、WhatsApp，所有这些。

Boris：而团队当时做的事情之一，就是提升生产力。那时候，能看到生产力提升个 2% 之类的，就已经是几百号人干一年的成果了。所以这个 100%……这简直闻所未闻，完全闻所未闻。

主持人：是什么驱使你来到 Anthropic？我是说，作为一个 builder，你哪儿都能去。是哪个时刻让你觉得：就是这群人了，或者就是这条路了。Boris：我当时住在日本乡下，每天早上打开 Hacker News 看新闻，然后到某个时候，新闻就开始全是 AI 的东西了。我开始用其中一些早期产品，我记得头几次用的时候，那种感觉真的让我屏住呼吸——这么说有点肉麻，但那真的就是那种感觉。就是……太惊人了。作为一个 builder，我用这些非常非常早期的产品时，从未有过那种感觉。那大概是 Claude 2 的时代，或者差不多。于是我就开始和 Labs 的朋友聊，想看看发生了什么。然后我见到了 Ben Mann，Anthropic 的创始人之一，他一下子就把我折服了。而当我见到团队里其他人的时候，也一下子就被折服了。我想大概是两个方面。第一，它是作为一家 research lab 在运作的，产品非常非常小，真正重要的全是「构建一个安全的模型」，只有这件事要紧。所以这种「贴近模型、贴近研发、自己不再是那个最重要的东西——因为产品不再是了，模型才是那个最重要的东西」的理念，在我做了这么多年产品之后，真的让我很有共鸣。第二件事，就是它有多么使命驱动。我是个重度科幻读者，我的书架上全是科幻，所以我太清楚这件事可能变得多糟。

Boris：而当我在想，今年会发生什么的时候——它会彻底疯狂。最坏的情况下，它会变得非常、非常糟。

Boris：所以我就想去一个真正理解这一点、真正把这一点内化的地方。而在 Anthropic，你只要在食堂或者走廊里听到别人的谈话，大家聊的都是 AI safety（AI 安全）。这真的是每个人最关心、胜过一切的事。所以我就想去一个这样的地方。对我个人来说，使命太重要了。

主持人：那今年到底会发生什么？[笑声]

Boris：好。如果你回想一下六个月前，人们都在做什么预测。Dario 预测过，Anthropic 90% 的代码会由 Claude 来写。这已经成真了。对我个人来说，自从 Opus 4.5 以来，一直是 100%。我把 IDE 都卸了，我一行代码都不亲手改，100% 都是 Claude Code 加 Opus。我每天 land 大概 20 个 PR，天天如此。放眼整个 Anthropic，这个比例大概在 70% 到 90% 之间，取决于团队；很多团队是 100%，很多人也是 100%。我还记得，五月我们 GA Claude Code 的时候，我做过一个预测：你写代码将不再需要 IDE。当时说出来简直疯了，我感觉台下的观众都倒吸了一口气。

主持人：因为那在当时听起来真是个离谱的预测。但其实它无非就是——你只要沿着那条指数曲线走就行了。

Boris：而这就是深深写进 Anthropic DNA 里的东西——我们的创始人里有三位是 scaling laws 论文的共同作者，他们很早就看到了这一点，所以这就是在沿着指数走，这就是会发生的事，而它也确实发生了。那么继续沿着指数走，我认为接下来会发生的是：编程这件事，对所有人来说都会被「基本解决」。而我觉得今天，编程对我来说实际上已经解决了，而它对每个人也都会变成这样。无论哪个领域，我想我们会开始看到「软件工程师」这个头衔消失。也许会叫 builder，也许是产品经理，也许我们会把这个头衔当成一个残留的东西留下来，但人们做的工作，将不再只是写代码。软件工程师也要写 spec，也要和用户聊。就像我们现在在团队里已经开始看到的这样：工程师很大程度上都是通才，团队里每一个职能都在写代码——我们的 PM 写代码，我们的设计师写代码，我们的 EM 写代码，我们的……[清嗓子] 我们管财务的同事也写代码，团队里每个人都写代码。我们会开始看到这种情况出现在所有地方。所以这算是——如果我们只是延续现有趋势——这是下限。而上限，我觉得要可怕得多。这关乎我们触及 ASL4。在 Anthropic，我们会讨论这些安全等级。ASL3 是模型现在所处的位置，ASL4 是模型在递归式地自我改进。所以如果这真的发生，本质上，我们得先满足一堆条件，才能发布一个模型。而极端情况就是：这件事真的发生了，或者出现某种灾难性的误用——比如有人用模型来设计生物病毒、设计 0day，诸如此类。而这是我们正在非常非常积极地应对、以让它不要发生的事。我觉得，说实话，这一路真的既令人兴奋又令人谦卑——看到大家是怎么用 Claude Code 的。我当初只是想做一个很酷的东西，结果它变得非常有用，这太让人意外、太让人兴奋了。

主持人：我从 Twitter 上、或者说从外部得到的印象，基本上是：所有人都在假期里消失了，然后一回来就听说了 Claude Code，从此就彻底疯了。你在内部也是这种感觉吗？你是不是也过了一个美美的圣诞假期，然后回来——发生了什么？Boris：其实整个十二月我都在到处旅行。我休了个「编程假」——我们到处旅行，而我就是每天写代码，那感觉特别好。然后我那会儿也开始用 Twitter，因为我很久很久以前做过 Threads，所以我一直是个 Threads 用户，我就想看看别的平台上大家都在哪儿。对，我想对很多人来说，那个假期就是他们发现 Opus 4.5 的时刻。而我算是早就知道了。

Boris：嗯。

Boris：而在内部，Claude Code 这条指数曲线已经狂飙了好多好个月了，所以那条线就是变得更陡了而已。这就是我们看到的。而你现在看 Claude Code——Mercury 有个数据说，70% 的创业公司都把 Claude 选为他们的首选模型；SemiAnalysis 还有另一个数据说，所有公开 commit 里有 4% 是 Claude Code 写的——是全世界所有地方写的所有代码里的 4%。从最最大的公司到最小最小的初创，所有公司都在用 Claude Code。它甚至为 Perseverance、为那台火星车规划过航线。对我来说，这就是最酷的事。我们甚至还印了海报，因为团队都觉得：哇，NASA 居然选择用这个东西，太酷了。所以，对，这让人谦卑。但它也感觉像才刚刚是开始。主持人：那 Claude Code 和 co-work 之间，算是什么样的互动关系？它是 Claude Code 的一个 fork 吗？还是说，你让 Claude Code 去看 Claude Code，然后说：咱们为非技术人群写一份新 spec，把所有经验教训都保留下来，然后它就自己跑几天把它做出来了？它的起源是什么，你觉得它会走向哪里？

Boris：这大概是我第五次用「潜在需求」这个词了。就是那样——我们在看 Twitter，有个家伙在用 Claude Code 监控他的番茄植株。

主持人：嗯。

Boris：还有另一个人在用它从一块损坏的硬盘里抢救婚礼照片。还有人拿它做财务。我们看 Anthropic 内部，每个设计师都在用，整个财务团队到这会儿都在用，整个数据科学团队都在用——而且都不是用来写代码。大家想尽办法、翻山越岭也要在终端里装上这个东西，就为了能用上它。所以我们早有一段时间就知道，我们想做一个东西，于是试了一堆不同的想法，而真正跑起来的，就是一个套在 GUI 里、放在桌面应用里的 Claude Code 小外壳，仅此而已。它的底下就是 Claude Code，是同一个智能体。

主持人：哦，哇。

Boris：而 Felix 和那个团队——Felix 是早期的 Electron 贡献者，他对那套技术栈非常熟——他一直在捣鼓各种点子，他们大概用了 10 天就把它做出来了，100% 都是 Claude Code 写的。而它就是感觉已经准备好发布了。为了非技术用户，我们得做很多东西，所以它和技术型用户群体还是有点不一样：所有代码都跑在一个虚拟机里，有很多针对删除的保护，有很多权限提示，还有一堆给用户的护栏。说实话，这挺显而易见的。主持人：Boris，非常感谢你做出了一个让我睡不着的东西，但作为回报，它让我重新找回了「创造者模式（creator mode）」，找回了某种「创始人模式（founder mode）」。这是令人振奋的三周。我真不敢相信自己从十一月一直等到现在才真的开始用它。非常感谢你今天和我们在一起，感谢你正在构建的东西。

Boris：谢谢邀请。还有——把 bug 发过来。[笑声]
