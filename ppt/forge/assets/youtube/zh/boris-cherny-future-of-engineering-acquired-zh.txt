主持人：好，那我们需要听一下起源故事。Claude Code 是从哪里来的？
Boris：顺便说一句，坐在这里听到你们的声音真的很魔幻，因为我平时是戴着耳机听你们节目的，而且大概是 2 倍速，估计是 2 倍速（笑）。2 倍速，再叠加我们剪片子时处理掉的那些口头小毛病之类的。是啊，这件事在很多方面都算是个意外。我在 2024 年底加入了 Anthropic 的一个团队，那是个偏原型的团队，叫 labs 团队——我们后来把它重新启用了——当时的想法是搞清楚下一个重磅产品是什么，同时把模型的能力前沿往前推，并弄明白该如何改进模型，让它最好地支撑那个尚未被造出来的未来产品。但很难知道该把模型往哪个方向演进，因为除非有一个真正把前沿往前推的产品存在，否则你根本无从判断。而当时有一种非常强烈的「产品悬置（product overhang）」感：模型能做一大堆事情，却还没有任何产品把这些能力真正接住。

主持人：你想想当时的编程工具，基本上就是自动补全工具。你可以问智能体（agent）一个问题，但它写不了代码。
Boris：对、对、对。而且直到不久之前，模型就是不够好，真的做不到。所以我们觉得完全可以放手一搏，做一个纯粹就是「编码智能体」的产品。我们把它做出来了，但一开始很烂。有相当长一段时间，它大概只能替我写 10%、20% 的代码。
主持人：稍等，回到这一刻之前——当时在 Anthropic，编程这件事处在什么状态？它受重视到什么程度？
Boris：当时在 Anthropic 内部，我们还在用 IDE。但作为一家公司的 Anthropic，一直很在意编程，一直很在意工具使用（tool use），一直很在意计算机使用（computer use）。这一直都是我们的核心研究方向，因为对我们来说，我们存在的意义就是研究 AI 安全。这就是我们存在的理由。你随便在 Anthropic 的走廊里拦住一个人问「你为什么在这儿」，他都会说 AI 安全。公司里每一个人——包括我——都深信这是需要解决的头号难题，而解决它有很多种路径。你可以研究机制可解释性（mechanistic interpretability），可以做对齐（alignment）工作。

Boris：研究模型的方法有很多种，可以在培养皿里研究，但归根结底你必须在真实环境里研究它，看看它在其他方面都安全了之后会做出什么。Claude Code 大致就是从这里切入的。对 Anthropic 这家公司来说，方向从来都是安全，而研究安全有很多层，其中就包括把模型放到真实环境里；那么一个有用的做法是什么呢？是编程，因为编程是模型与世界交互的方式。所以如果你想研究各种各样的模型失准（misalignment），你就得让它足够有用、好到大家都去用它，这样你才能研究它——而编程就是一个显而易见的应用场景。这一直是我们的重点，从一开始就如此。
主持人：这是一个干净得令人难以置信的宇宙，因为你有这么多训练数据。它要么能跑、要么不能跑；而且取决于语言，它要么能编译、要么不能编译，总之有一种非常清晰的「通过/失败」的可检验方式。而且它的正确解空间是非常受限的。英语里有无数种正确又优美的诗，但针对某个问题写出正确代码的方式，数量是有限的、并非无限。
Boris：对。鉴于这一点，把它当作你的培养皿来用，有一种内在的优雅。
主持人：是的，正是如此。说起来，你知道 Hofstadter 吗，就是写《哥德尔、艾舍尔、巴赫》（Gödel, Escher, Bach）的那个人。有人读过吗——对、对、对、对。好书，真的很好。

Boris：但他在 80 年代还写过另一本非常怪的书，讲的是他对通往人工智能之路的想法，因为他是个教授，在学校里教 AI，当时就在教书。他谈到认知的基础、智能的基础是识别模式，而他研究这一点的方式之一，来自他的一个爱好——把诗歌从英语翻译成法语。直译很少是正确的译法，里面其实要投入大量的品味，有时你得稍微「糊弄」一下，好让韵律成立，做法多种多样。
主持人：是啊，那是个模糊的问题，但编程我觉得更容易解决。它在商业上也非常有价值，所以这能帮我们做一门生意；而且这正好是我们最喜欢的客户——企业、初创公司、各类公司——都有的那类生意，所以它能让我们拥有一个一致（aligned）的商业模式。这样我们就不用做广告了，可以专注于我们在乎的安全，它能帮我们建成一家让我们真正去做这件事的公司。顺带问一句，你来 Anthropic 之前在 Meta，在 Meta 时你很关注代码。我很好奇，现在回过头把点连起来看，你在 Meta 做的事情如何影响了 Claude Code 的开端？
Boris：对我来说，做开发者工具（DevTools）一直都是个副业，从来不是主业。

Boris：而我觉得这恰恰是做 DevTools 最好的方式，因为你要专注的是解决一个业务问题，做出一个人们喜欢、对人们有用的东西——这才是我们作为工程师在这里的根本目的。至少 YC 会把这一点狠狠灌输给你，我深有同感。
主持人：你以前参加过 YC 吗？
Boris：对、对。我其实是一家 YC 公司的第一个员工，大概是 2010、2011 年那会儿，差不多是最早的几批之一。
主持人：哇，厉害。
Boris：所以对我来说，DevTools 一直是这种副业性质的存在。我做产品，而在做产品的路上，如果开发体验（DevX）不够好，我就会做工具把它改善一点。我一直都是这样处理问题的。所以在这里，我也只是套用了那种心态——先为自己做一个东西出来，然后希望它对别人也有用。

Boris：结果我很惊讶地发现，它确实有用，这太棒了。
主持人：你刚才说它一开始挺烂的，你只敢把 10% 的工作交给它，或者说它只能做你 10% 的工作。早期的瓶颈是什么，你们又是怎么解决、让它变好的？因为据我所知，你已经差不多六个月没在工作里写过一行代码了。
Boris：是的。这跟「它只能做 10%」已经是天壤之别了。是什么变了？我记得很清楚。5 月那会儿是 Sonnet 4 和 Opus 4，到了 11 月是 Opus 4.5。变的就是底层模型，就是模型本身。当然，harness 上也做了大量工作，让 Claude Code 变得更好这件事上也投入了很多。你要知道，每个人都喜欢按自己的方式用这些东西——这就是为工程师做产品的特点：这不是一个消费品，因为工程师对自己喜欢怎么用一个东西非常有主见。所以我们一开始做的是 CLI，后来又做了桌面应用、移动应用，做了 iOS 和 Android 应用，还有 Slack 应用、GitHub 应用——你可以用任何你想要的方式使用 Claude Code。这中间有大量是我们在创新、在学习、在摸索哪些功能真的有用。比如 plan 模式（plan mode）就是这么来的，很多不同的工具和体验都是这么来的。但根本上，当我想那些阶跃式的变化、想模型到底写了我百分之多少的代码时，关键就是模型——模型变强了，于是那个比例就一路上升。

主持人：在你能谈的范围内，Claude Code 当时获得的体验，有多紧密地反哺到了通往 4.0、4.5 等等的模型工作上？
Boris：Anthropic 里的每个人每天都用 Claude Code。所以做模型的研究员在用 Claude Code，做产品的人也在用 Claude Code，本质上就是这样一个循环。
主持人：你这边有没有什么指标，能用数字描述它到底在多大程度上改变了公司的轨迹？因为从外面看，你们现在发布的产品比过去多得多，一个很合理的推测是，这是因为你们全公司都在内部用 Claude Code。那该怎么准确衡量其中有多少真正归功于 Claude Code？
Boris：嗯，在一家 AI lab 里待着，你会慢慢习惯用指数的方式思考问题，基本上所有图表都是指数的。所以我们几乎对所有东西都用对数—线性（log-linear）图：x 轴是线性的，y 轴是对数的。于是一切都是指数的——收入是指数的，用量是指数的。这是作为工程师能遇到的最有意思的问题，也谢谢你们一直包容。本质上一切都在往上走，包括代码量也是。我们看自发布 Claude Code 以来，Anthropic 的人写的代码行数、写的 PR（pull request）数量，这些都涨了好几百个百分点。我们最近一次对外分享的数字大概是 3 倍之类的，但这其实已经严重过时了，现在要高得多。

主持人：那个 3 倍指的是什么？
Boris：是 Anthropic 里每个工程师人均写的代码量。
主持人：明白了。
Boris：所以工程团队的规模扩大了很多倍。而通常工程团队规模扩大时，生产力会下降。我在 Meta 的时候，我的职责之一就是所有代码库的代码质量，我们在意这件事是因为它对生产力有用——代码质量高，工程师就更有生产力，我们当时用实证方式证明了这一点。通常会发生的是代码质量变差、生产力下降。另一件会发生的事是，随着工程师人数增加，生产力也会下降，因为新人会一直问老工程师「这个怎么做、那个怎么做」，于是被问的工程师就没法写代码了，而且还要花上手时间。而我们在 Anthropic 看到的第一件事就是：新人加入后，上手时间大概是两天——过去这可是几周，现在是两天，因为你直接问 Claude Code 就行。我们还得跟新加入的人解释：比如有人问「我怎么查数据库」，答案就是打开 Claude Code，在 Claude 代码库里跑起来，让 Claude Code 去查数据库，因为有一个查数据库的 skill，它就是知道怎么查。

主持人：那你们 2026 年新招进来的工程师里，有多少人是写过任何代码的？
Boris：呃，那得先定义什么叫「写代码」。
主持人：对、对。（笑）等等，那你怎么定义写代码？
Boris：你知道吗，对我来说，工程这件事从来都是……我爷爷当年是用打孔卡写程序的，在苏联——对他来说，编程就是一张纸、往上面打孔，再把它喂进一台大机器里，机器吭哧吭哧跑一会儿，然后给你答案，那就是编程，对吧？就像我爸爸写了大量汇编，他会笑话我写 Python，说「你这哪叫写代码」。
主持人：没错，没错。对「真正的工程师」来说这不算，或者说这太高层了。
Boris：但这正是编程的本质——抽象层级一直在上升。它从拨动开关，到打孔卡，到汇编，再到 COBOL、FORTRAN、Java 这些高级语言，然后到 JavaScript、Python 这些真正的高级语言。这件事一直在发生，我把我们正在做的事看作这条连续谱上的某一点。所以对我来说，一年前我写代码的方式是在 IDE 里写，配合某种自动补全。到了 11 月，我把 IDE 卸载了，因为我根本不用它（笑）。我就是……过去一个月我一次都没打开过它，那就卸了吧。
主持人：哇。
Boris：到那个阶段，我大概同时跑着 5 到 10 个 Claude Code 实例并行，我的「写代码」就是给 Claude Code 下提示（prompt）让它去写代码。而现在我觉得又升到了下一个抽象层——我已经不再给 Claude Code 下提示了。

Boris：我有一些 loop 在跑，是它们在给 Claude 下提示、在弄清楚接下来该做什么。我的工作变成了写 loop。我觉得这就是我们接下来几个月、也许到今年年底之前会看到的一次转变。
主持人：哇。假设我——显然是假设的我，不是真的我——是一个想加入 Anthropic 工程团队的工程师，你今天会怎么评估我？（笑）
Boris：就我们团队、尤其是就 Claude Code 而言，我看重的一点是：我们非常喜欢通才（generalist）。大概六个月前我们开始观察到一件事：团队里几乎没有什么工程师还在做传统意义上的「工程」——也就是用户研究员去跟用户聊、把结论写成文档交给设计师、设计师出 mockup、再交给产品经理（PM）定范围、最后交给工程师去实现。我在微软待过，对这套流程熟得不能再熟（笑）。过去就是这样的。但我们意识到，团队已经不再是这么运作的了。我们团队本来就比这更偏原型一些，但大概六个月前我们发现：团队里每个工程师都在做范围界定（scoping），每个人每天都跟用户交流，工程师也在做设计，每个人都能自如地拉数据、做数据科学工作、搭仪表盘之类的。所以我觉得我们开始看到所有角色正在融合、融化成一个「建造者（builder）」。Satya 好像就是这么叫的，大概就是这么个东西。它几乎像一个产品工程师（product engineer），但你甚至不一定非得是个工程师。
主持人：没错。而且我们确实有设计师在 ship 代码，我们的财务同事在 ship 代码，我想我们的 chief of staff 也在 ship 代码。其实我们在 Acquired 的所有基础设施，现在都相当迅速地迁移到了 Claude Code 上。这也是为什么——我能讲一个 Acquired 的小趣事吗？我们是音频播客，YouTube 没有只上传音频的方式，你必须上传一个视频，而它最好还得有点看头。

主持人：所以很长一段时间里，它就是一个黑屏的 MP4（笑）。有个字幕（transcript）会是个不错的主意，但我们还没有字幕，因为人工做字幕要花一周时间。幸好有 AI。总之，我——好吧，是我和 Claude——胡乱写了一整套 Claude Code 脚本，然后在某个节点我把它甩给了 David，说「你能不能接着把这个搞下去」。一开始还有点抵触，但后来你确实拉起了一个……我喜欢这个。
Boris：对、对、对。
主持人：打开终端这件事——David 上一次打开终端，还是大学 CS 课结束后的某一天，那是他最后一次打开终端。而就在那之后的一天，Co-work 发布了。Co-work 的卖点是：你想要 Claude Code 的全部能力，但你不想碰终端、不想敲命令、不想装 npm，诸如此类。我们其实是听说 David 不得不打开一个终端，于是我们说「我们必须把这个发出去，我们只有一天时间」。我想拿这个当引子，请你讲讲 Claude Co-work 的故事，因为在我看来，Claude Co-work 面对的市场要大得多——不想打开终端的人，远比会打开终端的人多。有意思的是它先走向了 Claude Code 这个方向，然后——说实话——过了相当长一段时间，Claude Co-work 才出来。
Boris：对，没错。说真的，就是这个故事，差不多就是这个故事的某个版本。4 月的时候，我记得我走进办公室，紧挨着我们几个做 Claude Code 的人坐的地方，坐着几个数据科学家。我走进去，其中一个数据科学家屏幕上正开着 Claude Code，而那时候 Claude Code 还只能在终端里用——还没有桌面应用，还没有移动应用，所以你真得知道自己在干什么。我就问 Brandon：「哥们儿，你这是在干嘛？是在内部试用（dogfooding）吗，还是就想搞明白这东西是啥？」因为他刚加入团队。

主持人：那你们砍掉了哪些其他路径？因为如果让我来定义这份创意简报，它会是「把 Claude Code 的全部能力，交给那些不想打开终端的人」，但这并不是一一对应的翻译。你必须在自己做的产品里有所取舍、有所主张，才能吃下 Claude Code 能做的其中一部分工作。
Boris：我们试过，天啊，我都记不全所有原型了。我们试过一个基于 Slack 的方案，但不太行，因为把一个 Slack 聊天机器人做得体验好实在太难了。我们试过基于 web 的方案，有一堆不同的 web 原型，我们都不太确定，没有一个感觉特别好。待在浏览器里总有点不对劲。而且如果它在浏览器里，就访问不了你所有的工具——我桌面上有个 Word 文档，我没法让浏览器里的东西去处理它。文件系统访问感觉是必须的。而光是「得把文件拖拽到浏览器里」这一点点摩擦，就足以让体验变得不好。我觉得这又回到我们思考产品的方式：我们做我们自己爱的东西，你要做一个你自己会爱上、每天都会用的产品，然后也许有些用户也会喜欢，希望它对其他人也有用。
主持人：我有一点挺意外的：我的 Claude Code 用量下降了，因为大量 Python 是在 Claude 的聊天窗口里写出来的——我会问一些需要大量数据分析的问题，然后我能看到「哦，它现在正在写一些软件来做这个分析，接着它会写一堆 HTML、CSS 和 JavaScript，然后渲染一个全新的 UI 让我去玩」。这背后用到了大量的 Claude Code 生成，尽管我一次都没有直接跟 Claude Code 这个产品交互过，事情就办成了。

Boris：对、对。这里有个挺有意思的理论问题：你到底想在什么时候做计算？是想在从模型采样、做推理的时候实时计算，还是想预计算（precompute）——也就是让模型写一个程序，然后你可以反复运行这个程序，这对你来说是免费的。我们本质上想尽可能多地做后者。但这其实取决于模型——这又回到那个点：模型以软件的形式存在，它需要一种与世界交互的方式；既然它以软件的形式存在，那么它做这件事的方式就是编程，这是它天生会说的语言，是它理解的东西。所以从 Claude Code 最早的日子起，第一个版本我就给了它一个 bash 工具，让它能在我的电脑上跑命令。我没有告诉它任何关于这个工具的事，它自己就琢磨出怎么用了。我有个讲过一千遍的轶事：我问它「我在听什么音乐」，它打开 bash 工具，写了个小程序，这个程序又写了一段 AppleScript——我自己从来没写过 AppleScript。它写了那段 AppleScript，打开我的音乐播放器，然后说「这是你正在听的歌」。

Boris：而即便在那个时候，那还是 Sonnet 3.5，算不上多聪明的模型——它是当时最好的，但按现在的标准来看并不怎么聪明——可它就是知道该怎么做这件事。所以写代码这件事、用工具与世界交互这件事，里面有种东西是模型天生就想做的。
主持人：我想把产品相关的具体问题先放一放，问一点关于文化和组织设计的事。你的头衔是「技术成员（member of technical staff）」，我想很多人都有这个头衔（笑）。这到底是怎么回事？有什么利弊？你会推荐给在座的各位吗？
Boris：好。最糟糕、也让我刚加入时挺烦的一点是：你在 Slack 上给某人发消息，结果只显示「技术成员」，于是你会想：这人是个设计师吗？是工程师吗？是个经理吗？你根本不知道。他们到底在做什么？在做什么？你完全不知道。我其实非常喜欢这一点。

Boris：我在 Meta 的时候，有一件我很喜欢的事是：每个软件工程师的头衔都是「软件工程师（software engineer）」，没有「高级软件工程师」「首席软件工程师」之类的。
主持人：哦，真的吗？
Boris：对，根本没有这种东西。
主持人：哈。
Boris：我喜欢它，是因为如果你给别人挂上「资深」的头衔，有时他们会提出一些烂想法，而其他人出于尊重就直接照做了；但其实他们应该反驳。让每个人在这一点上处在同一水平线上，是一种非常好的文化强制力（forcing function）。
主持人：但层级这东西还是会透出来吧——「对，我知道你只是个软件工程师，我也只是个软件工程师，但我很清楚你是某个级别的软件工程师」，哪怕它没写在你的头衔里。
Boris：有时候你知道，但很多时候你并不知道。我在 Facebook 的时候，刚加入是个 L4 工程师，我有个想法，就去找了 connectivity 的 VP，跟他说「这是我的想法，我们一起把它做出来吧」，而他根本不知道我是什么级别——这挺有意思的——那是个烂想法，最后没成；然后我又跟另一个 VP 干了一次，也没成；但第三次成了，于是我们拉起一个团队开始做事，然后才转向下一个想法。这种事我现在一直都能看到。团队里的人还抱着那些老派的资历观念，但那种感觉就像——在很多方面这都不重要了。那些有 20 年、30 年经验的工程师，他们得忘掉太多东西，你得花好几个月教他们忘掉那些已经毫不相干的旧习惯；而有时一个应届生加入团队，反而会教我怎么把 Claude Code 用得更好，因为他们是原生地那样思考的，而这并不是我的本能。更难的是，每出一个新模型，你都得重新校准、重新学习。但回到「技术成员」这件事，我觉得它其实非常重要，因为所有那些关于工程师 vs 产品经理 vs 设计师 vs 用户研究员的旧区分，到年底都会消失。所以这能帮我们今天就把这一点看得非常清楚，并按此行动。我觉得在一家 AI lab 里你必须这么做：推动每个人都更像 AGI 那样去构建，更多地以这种方式去思考未来。

主持人：我很好奇，顺着这个往下，能否稍微推广一点——对在座所有的创始人、所有的公司来说，他们现在该为自己的组织考虑些什么，以迎接年底？你觉得创始人和公司在未来几个月里，心态上必须改变什么？
Boris：如果要我现在就做一件事，我会给每个人尽可能多的 token——当然，我这么说是因为我在一家 AI lab 工作（笑）。引用 Jensen 的话：「买得越多，省得越多」（笑）。所以我会从这里起步：给人们尽可能多的 token，让他们去实验。我要做的另一件事是，把每个项目都稍微少给点资源（underfund）。如果你在做的一个项目，你觉得「这大概需要 4 个工程师」，那就放 2 个工程师上去，再给他们一堆 token，让他们想办法搞定。多半他们能搞定，可能有一大堆东西他们能自动化，有一大堆东西他们能精简（streamline），而且正因为他们把它自动化了，下次就能做得更好、更便宜。当然，这里面还有复利效应。
主持人：除了 token 之外，资源更少本身也会带来复利效应。
Boris：没错。这有点像做业务、做产品：你要做的决定太多了，所以有一套原则会非常好，这样你就可以依靠这些原则，而不用每次都临时拍板。创始人和公司常常有这些「原则文档」，这有点像那个，但模型也能用这些原则——它以 skills 的形式出现。当然，如果某个用例起飞了、吃掉一大堆 token，那时你再进去优化它、把它做高效。但总的来说，如果让我把这条建议复述给你听——用更少的人 staffing，把预算从人转移到 token——它的产出就是抬高你的前期成本、降低你的持续成本，因为……这几乎像是预编译（pre-compiling）：你 upfront 先做完一大堆工作，于是那些一遍又一遍重复的任务就变得容易、变得顺滑了。
Boris：对、对，可以这么理解。而且因为你放上去的人更少，这意味着你公司里的每个人能做得多得多。

主持人：在我看来，这像是组建团队这件事最大的一次清算：人们很习惯拥有一个头衔、一门学科，人们以「我是一个好 PM」而深感自豪——「我要写一堆关于产品这门学科的博客文章」。外面有大量这样的人，或者设计师——「我等不及要展示我那些漂亮设计组成的作品集了」。难道我们在 12 个月内，都必须甩掉「我是某个什么角色」这个想法，让所有人都变成一袋灵活的 token 生成器？
Boris：哇，Ben，你也太乐观了（笑）。我可能会用稍微不同的措辞，但差不多就是这么回事。
主持人：你应该把这句话印到 T 恤上（笑）。
Boris：我觉得大概就是那么回事。就我个人而言，我当工程师有一阵子了，但我一直戴着不同的帽子——我创过业，做过业务，做过产品，做过用户研究，做过设计。所以对我个人来说，我就是热爱做产品，我不在乎自己戴的是不是工程师这顶帽子。而现在我看到这一点正在被印证。所以是的，我觉得现在就是通才的黄金时代——那些想做不止一件事的人，从来没有这么有趣过，也从来没有这么容易过。
主持人：也许再问一个问题。我们之前跟 Garrett 聊到过一点，我很好奇你的看法。你怎么看「品味（taste）」——无论是你个人，还是 Anthropic？

Boris：我觉得每一次，当我觉得自己写代码的方式有什么特别之处时，结果我都错了。我曾经对我们写代码的方式有一大堆主见。比如我非常喜欢函数式编程，所以我喜欢 Haskell、Scala 这类怪怪的函数式语言；而在最开始，我给我们代码库定过一条规矩：代码库里没有类（class），只有函数（function），因为那就是我写代码的方式，是我喜欢的方式。结果到了周末，工程师们开始偷偷塞进一些带类的改动，我周一就会发现，然后把那些 PR 拎出来说「不不不，别这么干」。后来在某个时刻，模型开始写所有的代码，而它开始写类，我就想：「好吧，也许模型是对的，也许我这个主见挺蠢的，只是我独有的这点偏好。」但其实无所谓，因为业务结果达成了，而且达成得更快，代码其实也不差——而且显然代码一直在越变越好。所以我觉得每一次，当我有那种「我在某方面很特别」的感觉时，我常常被证明是错的。而我觉得就当前模型的能力而言，人们谈论很多的一点是：alpha（超额优势）在于产品品味。

Boris：而我觉得这一点也会消失。这是今天的 alpha。但现在我有几千个 Claude Code 实例在跑着做事，其中一大批在看 Twitter 上的反馈，在看 GitHub issues，在看 Slack，在弄清楚接下来该做什么。眼下大多数想法都是烂的，但也许有 20% 是好的。如果你等下一个模型，往后推算大概 3 个月、6 个月，大多数想法可能都会是好的。而且会有某种新东西出现，会有别的东西被侵蚀掉——猜猜那会是什么？有没有什么最终的东西，是人类独特擅长的？我觉得我们最后要教给模型的东西是价值观，以及如何成为——也就是我们如何教我们的孩子成为好人——我们要教模型如何成为一个好模型。
