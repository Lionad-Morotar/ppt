# 技术分享讲稿撰写与压缩指南

用于将长篇论文、技术书籍、技能库（如 `SKILL.md` + `chapters/`）或工程实践沉淀，转化为节奏紧凑、有判断力的技术分享逐字讲稿。

## 1. 核心立论：给尺子，不背编年史

一场高质量的技术分享只解决两件事：

- 给听众一把可复用的判断尺子：遇到某类技术两难时，按哪几条判据做取舍，怎么验证它真的有效。
- 用第一手案发现场代替抽象教条：用真实的本仓事故、历史废案、正反对照实验来支撑结论，而不是罗列特性清单。

动笔前先在讲稿顶部写清「刻意不讲」清单：凡是听众能自己看文档学会的 API 细节、底层数学推导或无关支线，一律在备忘中显式剔除，防止挤占核心主线时间。

## 2. 30 分钟分享的标准五幕弧线

以 30 分钟（约 27 分钟主讲 + 3 分钟收束）为例，控制在 12 至 15 张核心幻灯片：

- 开场破题（3 分钟，2 页）：用 2 至 3 个极具反差感的真实怪癖、线上病例或业务痛点切入，撕掉表面刻板印象，抛出全场唯一的核心立论。
- 第一幕：源头与第一性约束（5.5 分钟，3 页）：还原系统或技术诞生时的硬约束（排期、商业边界、存量兼容），提炼出底层架构的取舍逻辑。
- 第二幕：博弈规则与旁路突围（5.5 分钟，2 页）：拆解平台或团队演进中的硬闸门（为什么单边硬改必败），展示如何在不破坏存量的前提下通过运行时、封装层或编译层突围。
- 第三幕：失败样本解剖与踩刹车信号（6 分钟，3 页）：正面剖析历史上的溃败案例或本仓反例，搭配「同一设计在不同宿主下的一成一败」对照实验，提炼出可量化自检的踩刹车红线。
- 第四幕：死局自救的工程手术（6.5 分钟，2 页）：拆解走出泥潭的 3 至 4 套核心工程手法（如减法式方言、单人倡导者漏斗、最小安全内核、测试即规范）。
- 收尾：带回工位的随身决策卡（3.5 分钟，2 页）：把全场模型收敛为 6 个日常研发局面的判断指南，以一句有力的金句收束并进入提问环节。

若时长扩展为 45 或 90 分钟，按比例增加「现场演示（Live Demo）」与「本仓实测病例」，但主线依然保持「立论 → 正反样本 → 工程机制 → 随身决策卡」四段骨架。

## 3. 讲稿文件结构约定

讲稿统一保存在目标分享目录 `ppt/<slug>/script-<duration>min.md`（或 `thoughts.md`），包含四个固定部分：

- 讲者备忘：列出各幕次时段、时长、核心心智模型与「刻意不讲」的自律边界。
- 逐页讲稿与幻灯片锚点：每节标明对应的 Slide 标题、屏幕展示要点与口播逐字稿，口播采用自然的同行交流语态，少用书面套话。
- 经典金句与术语锚点：提炼 2 至 3 句能让人记住的短句，供幻灯片尾页与过渡页引用。
- 随身决策矩阵：以「日常局面 → 判断尺子 → 采取动作」三要素收口，让听众离场即可复用。
